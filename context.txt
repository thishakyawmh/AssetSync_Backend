# University Resource Allocation System - Project Context

## Project Overview
This project is a University Resource Allocation System designed to manage both movable hardware equipment (e.g., projectors, cameras, speakers, etc.) and physical stationary locations (e.g., lecture halls, seminar rooms, auditoriums, etc.). 

---

## Core Modules

### 1. Location Allocation Module (Batch Processing)
Instead of traditional first-come-first-served fulfillment, venue bookings for locations are handled through batch processing:
* **Booking Window:** Users (students and lecturers) submit requests up to 24 hours prior to the required time.
* **Allocation Process:** The system collects all incoming requests and processes them at the 24-hour mark. It evaluates data such as attendee count, event type, and lecturer requirements to allocate the most suitable venue automatically.
* **Notification:** Once allocated, requesters and attendees receive updates and notifications via an integrated system calendar and emails.

### 2. Equipment Allocation Module (Real-Time Booking)
Physical hardware devices require immediacy, which is supported by real-time transaction processing:
* **Inventory Management:** Administrative staff can digitize and manage the physical hardware inventory, inputting detailed parameters such as asset categories, quality metrics, and total quantities.
* **On-Demand Booking:** End-users can interact with dynamic, live availability timetables to instantly reserve and check out available hardware items.

---

## Core Features & Conflict Resolution

* **Automated Alternatives Engine:** Instead of hard-rejecting booking requests when a conflict occurs or a resource is unavailable, the system queries the database to suggest viable alternatives (e.g., a similar testing device, or the requested room at a different time).
* **Unified Central Dashboard:** A high-visibility, transparent visual dashboard displaying confirmed times, active asset locations, and event metadata to ensure complete institutional visibility.

## Implemented So Far (The Foundation & Resource Ledger)
The initial backend foundation has been built with the following components under the package `com.innov8.AssetSync`:

1. **Database Schema Specifications (`Resource.java` in `model` package):**
   * A single unified entity representing both stationary locations and movable equipment.
   * Fields: `id`, `resourceType` (Enum: `LOCATION`, `EQUIPMENT`), `name`, `category`, `capacity` (applied to Locations), `quantity` (applied to Equipment), and `qualityStatus` (applied to Equipment).
   
2. **Repository (`ResourceRepository.java` in `repository` package):**
   * Extends `JpaRepository<Resource, Long>`.
   * Includes custom derived query: `List<Resource> findByResourceType(Resource.ResourceType resourceType)`.

3. **Database Seeder (`DatabaseSeeder.java` in `seeder` package):**
   * Automatically seeds the database with dummy locations (Auditorium, Science Lab, Seminar Room) and equipment (Sony Camera, Mic Kit, Projector, VR Headsets) upon application startup if the repository is empty.

4. **REST Controller (`ResourceController.java` in `controller` package):**
   * Configured base mapping to `/api/resources`.
   * Enabled CORS for Vite React frontend via `@CrossOrigin(origins = "http://localhost:5173")`.
   * Endpoints:
     * `GET /api/resources` -> Returns all resources.
     * `GET /api/resources?type={type}` -> Returns resources filtered by `LOCATION` or `EQUIPMENT`.

5. **Configuration (`application.properties` in `resources` package):**
   * Configures local MySQL database connection with `ddl-auto=update` and dialect properties.

6. **Real-Time Equipment Booking & Conflict Validation (Feature 2):**
   * **Database Schema Specifications (`BookingRequest.java` in `model` package):**
     * Represents a booking request entity.
     * Fields: `id`, `resourceId` (foreign key reference to Resource), `requesterName`, `userRole` (e.g., `LECTURER`, `STUDENT`), `requestedQuantity`, `startTime`, `endTime`, and `status` (e.g., `ALLOCATED`, `CONFLICT`).
   * **Repository (`BookingRequestRepository.java` in `repository` package):**
     * Extends `JpaRepository<BookingRequest, Long>`.
   * **REST Controller & Logic (`EquipmentController.java` in `controller` package):**
     * Exposes `POST /api/equipment/book`.
     * Validates availability by checking if the resource exists and has enough inventory (`resource.getQuantity() >= request.getRequestedQuantity()`).
     * If validation succeeds, subtracts the requested quantity from the resource, updates the resource, sets the request status to `"ALLOCATED"`, saves the request, and returns `200 OK`.
     * If validation fails (insufficient inventory), sets the request status to `"CONFLICT"`, saves the booking request log, and returns `409 Conflict` with an error message: `"Insufficient inventory. Requested: X, Available: Y"`.

7. **24-Hour Batch Location Processor (Feature 3):**
   * **Database Schema Specifications (`LocationRequest.java` and `Allocation.java` in `model` package):**
     * `LocationRequest` holds location request details: `id`, `requestedCategory`, `requesterName`, `priority` (1: LECTURER, 2: STUDENT), `studentCount`, `startTime`, `endTime`, and `status` (default: `"PENDING"`).
     * `Allocation` maps request allocations: `id`, `requestId`, `resourceId`, `startTime`, and `endTime`.
   * **Repositories (`LocationRequestRepository.java` and `AllocationRepository.java` in `repository` package):**
     * `LocationRequestRepository` provides sorting by status and priority.
     * `AllocationRepository` contains a custom `@Query` check to detect overlapping booking allocations.
     * `ResourceRepository` contains a derived query to filter location resources by type, category, and capacity.
   * **REST Controller & Logic (`LocationController.java` in `controller` package):**
     * Exposes `POST /api/locations/request` to save new requests under `"PENDING"` status.
     * Exposes `POST /api/locations/process-batch` executing the batch scheduling algorithm. It matches location requests (prioritizing lecturers) against suitable resources, validating overlaps using `countOverlaps`, and creating `Allocation` logs while resolving remaining requests to `"CONFLICT"`.
